# Document templates

Companion to `CLEANROOM-RULES.md`. Copy, fill in, commit alongside the work.

## T1. Observation note (P2 / P3 only; lives in the local gitignored observation folder)

```markdown
# <area>: <what was observed>

- Date:
- Target and version / OS:
- Input used: synthetic, created from scratch (describe it in one line)
- Window capture: by window id, file name(s) in screenshots/ (never committed)

## Observed facts (own words)
- ...

## Open questions / not observable
- ...

## Decision taken (if any) and why
- ...
```

Rules: no pasted help text, no exported vendor files, no personal data (R5.6, R3.6).

## T3. Asset provenance record

Machine-readable form (one entry per asset file), with a generated human-readable index:

```toml
[[asset]]
path        = "assets/icons/example.svg"
title       = "Example icon"
author      = "Original work by <contributor>"          # or the upstream author
source      = "original work"                           # or URL + exact version/commit
license     = "MIT OR Apache-2.0"                       # SPDX expression
license_file = ""                                       # required if the licence says so
sha256      = "<hash>"                                  # mandatory for fetched assets
kind        = "icon"                                    # icon | image | font | sound | translation | data | ...
used_for    = "toolbar, embedded via <module>"
added       = "2026-10-09 by <contributor>"
modifications = "none"
vendor_origin = false                                   # true only for entries on the closed list in the profile (R8.3)
```

Plain-table alternative (when no tooling exists yet):

| Asset | Title | Author | Licence | Source (URL + version/commit) | Used for | Added |
|---|---|---|---|---|---|---|

Checks that must be able to fail the build: file without entry; hash mismatch; licence not on the
allowlist; licence file missing; name/metadata suggesting vendor origin (R11.1).

## T5. Pull-request checklist (paste into the PR template)

```markdown
### Clean-room
- [ ] No code, text or asset taken from the vendor or from a copyleft/competitor project
- [ ] Behaviour comes from: <spec/doc/observation> (listed in the module README)
- [ ] No files produced by the vendor's software are committed
- [ ] No screenshots of the vendor's software are committed
- [ ] New assets have provenance records; asset check passes
- [ ] No personal data in fixtures, metadata, paths
- [ ] Parity/status numbers are evidenced (measured vs estimated stated)
```

## T6. Violation or doubt report (R8.12 / section 14.5)

File it under `cleanroom/reports/YYYY-MM-DD-<slug>.md`, link it in STATE.md, and tell the owner
immediately. Use it for **confirmed violations** and for **doubts** (a source, asset or licence you
cannot clear). For a doubt the rule is: leave the material out, stop work that depends on it, file
this report with Status "suspected", and ask the owner.

```markdown
# <short title>

**Status:** suspected | confirmed | closed
**What:** <file / asset / text / source>
**Where:** <path(s), commit(s), branches; pushed? yes/no; published or packaged? yes/no>
**How it got there / why in doubt:** <task, source, tool>
**Rule(s) and source class:** <rule ids; S-class or "unclassified">
**Done so far:** <removed from working tree and outputs; work stopped>
**What would clear it:** <evidence that would settle a doubt>
**Needs owner decision:** <history purge, notification, re-implementation plan, exception ADR>
```

## T8. Parity tracker row

| Id | Feature (name only) | Source class | Status | Evidence |
|---|---|---|---|---|
| F-001 | <feature name> | S2 | planned / partial / shipped / out of scope | <test or command id; blank unless shipped or partial> |

Rules: "shipped" needs evidence that exists (check C6). Partial counts as partial. Out of scope links an
ADR. Status counts say whether they are measured or estimated.
